# Newarix defensive security audit and hardening

Date: 2026-10-06. Scope: repository, reachable local test services, dependency registry/advisories, production build and isolated regression tests. No production or third-party penetration tests, credential disclosure, stress tests, deployment, secret rotation, or service recreation were performed.

## Executive summary

Source and configuration review identified **0 demonstrated critical application vulnerabilities, 1 high configuration issue, 11 medium issues and 3 low issues**. Nine medium issues were fixed in code/dependencies; two remain architectural tradeoffs. Three low issues were hardened. The high issue is fixed in Compose configuration but **existing running containers still publish PostgreSQL and Redis on all host interfaces**. Applying that configuration requires a planned container recreation; no running services were disrupted during this audit.

The initial npm audit reported nine affected packages (five critical and four moderate ratings) arising from Seroval and esbuild advisories. These package ratings do not establish nine independently exploitable application vulnerabilities. The request-facing TanStack serializer was already newer than the affected Seroval versions; the affected older copy came through development tooling. Compatible overrides now produce zero reported vulnerabilities. This does not rule out unknown vulnerabilities.

Existing strengths include server-side user ownership, fixed parameterized queries, token-version session revocation on reset, expiring hashed recovery tokens consumed atomically, Google state/nonce/PKCE checks, CSP nonces, same-origin CSRF validation and normalized raster uploads. Hardening added request and processing limits, stronger password hashing, broader throttling, cache privacy, atomic tracking changes, safer redirects and links, dependency patches and sampled security events.

**Security Score: 69/100 — provisional repository-based assessment, not production certification.** Unknown infrastructure receives limited credit rather than being assumed secure.

## Architecture and attack surface

See [architecture map](architecture.md) and [endpoint-by-endpoint review](endpoints.md). React/TanStack Start SSR runs through Nitro/Vite, uses PostgreSQL via Drizzle and optionally Redis, calls AniList/Google/Resend and two image CDNs, and embeds sandboxed third-party players. Uploaded avatars are normalized WebP stored in SQL. There are no identified payments, admin panels, cron/workers, webhooks, custom GraphQL, archive extraction, object buckets or WebSockets/SSE.

## Fixed issues and behavior changes

- Login/signup inputs bounded; signup uniqueness races return a generic result through onConflictDoNothing. Signup still distinguishes success from an existing-account collision; full anti-enumeration requires a redesigned email-first registration flow.
- Login timing hardened, password hashing upgraded gradually, KDF concurrency limited to four. Password resets occurring during login cannot issue a session using an obsolete token version.
- Catalog requests limited to 240/IP/min; protected data calls to 120/account/min; profile updates to 10/account/15 min; avatar reads to 240/IP/min. Existing signup/reset/verification/OAuth/poster limits remain. These budgets may require measured tuning for legitimate shared-IP traffic.
- Cache bytes/counter cardinality, catalog queue and image-processing concurrency bounded. Production Redis failures deny calls using counters while cached content may fall back to memory. This deliberately trades availability during a Redis outage for abuse protection; alert on redis_security_unavailable.
- Request size/time controls run before JSON/multipart parsing and tolerate Nitro's Request proxy. Body buffering remains proportional to admitted connections, so edge admission controls are required.
- Lists limited to 1000 titles/account and favorites to 500/account; legacy larger lists/favorites are capped in responses without deleting stored data. Add pagination before raising these quotas. History pagination already exists; total history storage/aggregation is still unbounded over time.
- Transactions serialize list changes, toggles and quota checks, with atomic removal history. No database migration is required.
- Cache/referrer policy covers sensitive pages and RPC/errors; raster image endpoints retain their public caching. CSRF Origin/Referer fallback uses configured APP_URL; Sec-Fetch-Site same-origin still follows framework validation.
- Secure URL/redirect handling, avatar UUID validation, signed-32-bit media IDs and public avatar read throttles added.
- Sampled security events added for login failures, account creation, reset requests, password changes, rate limits and Redis security-store outages. Sampling records suppressed counts when the next event is emitted; it is not a complete audit trail or replacement for metrics/alerts.
- Secret ignore patterns expanded; compatible dependency overrides applied; test destination guards added; stale gallery selectors corrected.

## Secrets and frontend audit

Heuristic scans covered current tracked/untracked project files, all 141 unique reachable historical Git blobs, public files, build output and test artifacts. Candidates were synthetic credentials in test/config fixtures. No real committed credential was identified by these checks. Local .env values were read only internally for exact-match comparison with browser assets; no matches found, and no browser source maps were emitted. No credential values are included here. This is heuristic coverage, not a guarantee that every secret format was detected; dangling Git objects, external forks, remote logs and provider artifacts were not covered.

Development database credentials are intentionally documented and must never be production credentials. Do not overwrite real secrets with example values. If any development service was reachable by an untrusted party, rotate its credentials, investigate access, and treat Redis contents/session infrastructure as potentially compromised. Production secret entropy/storage/rotation and credentials outside this repository were not verified.

## Remaining risks and verification gaps

**Not verified — requires infrastructure/provider access.** Applies to hosting, DNS/subdomain ownership, live TLS/certificate/redirect configuration, WAF/CDN caching and DDoS protection, firewall/SSH/OS patching, production process privileges, database/Redis network exposure and encryption, database least-privilege roles, provider secrets, deployment protections, centralized logging/alerts, backups, retention and successful restores.

Do not interpret repository absence as provider controls being absent. No deployment/CI files were found, so production CI permissions and fork execution cannot be assessed. Container image tags remain mutable; no application Dockerfile exists. Existing development containers were inspected read-only and not recreated.

Other residual risks:

- Stolen-cookie logout replay and optional shared limiter configuration (M10/M11).
- Trusted proxy end-user IP integration is deployment-specific. Arbitrary X-Forwarded-For is deliberately not trusted; a proxy's shared peer IP may create shared quotas. Fix topology, not this by reflecting arbitrary headers.
- Redis maxmemory eviction can erase active security keys; separate cache and limiter storage or use a monitored non-evicting limiter database. DNS/network availability controls are outside application code.
- Strict poster host/path allowlists and rejected redirects block user-selected internal hosts. DNS resolution is not pinned/filtered; a compromised trusted DNS/CDN path remains a conditional SSRF risk. Enforce egress denial for internal/metadata ranges upstream without probing them here.
- No CAPTCHA, IP reputation, per-device session registry, MFA/passkeys, breached-password check or verified-email gate on tracking. Distributed bots can create accounts across IPs. These need provider/product decisions; no fake provider keys or ineffective User-Agent checks were added.
- Public session/status/options reads and OAuth callback still rely partly on upstream request limiting. History can grow over time; account quotas do not bound account creation globally.
- External API response shapes are typed/normalized but not comprehensively runtime-validated; upstream corruption can still cause controlled availability failures.
- Database pool has connection/idle limits; statement/lock deadlines should be configured on the production database role/pooler. Startup-parameter timeouts were not imposed because managed transaction poolers may reject them.
- Third-party sandboxed playback remains outside this project's security control; providers were not attacked or certified. Posters/fonts can reveal client network information by design.
- Registration collision results, OAuth existing-account errors, password-reset email-delivery timing and legacy KDF timing can still assist enumeration under their respective prerequisites.
- Provider request logs must redact recovery/verification query tokens and OAuth codes. no-referrer and no-store reduce browser leakage but cannot configure infrastructure logs.

## Priority plan

### Fix immediately

1. Plan a maintenance window to recreate only the development DB/Redis containers with loopback bindings, preserving the existing database volume. Do not use down -v. Confirm firewall coverage and rotate credentials if prior exposure was untrusted. The audit intentionally did not restart running services.
2. Deploy the reviewed application/lockfile changes through the normal release process; runtime remains unchanged until deployment. Set APP_URL to the exact HTTPS production origin and provide a high-entropy JWT secret through the provider secret store.
3. Verify shared Redis and trusted end-user IP handling before exposing multiple app instances. Alert on Redis failure; document the fail-closed behavior.

### Fix this week

1. Configure CDN/WAF endpoint budgets, bot challenges for signup/reset as appropriate, connection/admission limits, request/header/body deadlines, HTTP→HTTPS redirects and origin access restrictions. App throttling cannot stop volumetric DDoS.
2. Establish least-privilege database runtime/migration identities, encrypted provider connections and role-level query/lock timeouts compatible with the pooler.
3. Aggregate safe events/metrics, alert on abuse and failures, restrict logs and redact tokens/credentials. Review existing recovery-token URL logs.
4. Verify encrypted automated backups and perform a documented isolated restore. Retention alone is not evidence of recoverability.

### Fix this month

1. Introduce per-device revocable sessions and an account security screen; set a deliberate expiry/idle policy and add reauthentication for sensitive identity changes.
2. Add runtime schemas for upstream data and true pagination for legacy large lists/favorites; choose a history retention/quota policy without silently deleting user data.
3. Add CI security/type/test/build gates using immutable action SHAs, npm ci, least-privilege permissions, isolated test services and protected production environments. No untrusted fork workflow should receive deployment secrets.
4. Pin supported container digests and schedule updates; replace deprecated esbuild-kit tooling when the Drizzle upstream chain permits removing the compatibility override.

### Long-term

Introduce passkeys/MFA where justified, privacy-preserving bot challenges, verified-email privilege policies, tested disaster recovery/PITR, incident response exercises and recurring dependency/runtime/provider reviews. Re-score after infrastructure evidence and remaining session controls are available.
